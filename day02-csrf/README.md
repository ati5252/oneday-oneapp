# Day 2: CSRF（クロスサイトリクエストフォージェリ）対策

## 動かし方

```bash
pip install flask
python app.py
```

ブラウザで http://127.0.0.1:5000 を開き、`alice` / `alice123` でログインします（初期値が入っています）。

## CSRFとは

ブラウザは、あるサイトにリクエストを送るとき、そのサイトのCookieを自動で付けます。ログイン状態はCookieで管理されることが多いので、「ログイン中のブラウザから送られたリクエスト」は、サーバーから見ると本人の操作と区別がつきません。

CSRFは、この性質を悪用する攻撃です。ユーザーが別のサイトを見ているあいだに、そのサイトがこっそり本物のサイトへフォームを送らせると、ブラウザはCookieを付けて送ってしまいます。その結果、ユーザーが望んでいない「メールアドレスの変更」や「送金」などが本人の権限で実行されてしまいます。

ポイントは、攻撃者はCookieの中身を読めなくても、ブラウザに「送らせる」ことはできる、という点です。

## 対策1: CSRFトークン

サーバーは、ログイン中のユーザーごとに推測できないランダムな文字列（トークン）を作り、セッションに覚えておきます。そして、自分が出すフォームにはそのトークンを隠し項目として入れておきます。

POSTが届いたら、フォームのトークンとセッションのトークンが一致するかを確かめ、一致しなければ403で拒否します（`app.py` の `check_csrf()`）。

外部のサイトは、本物のサイトの画面の中身を読めないので、トークンの値を知ることができません。そのため、外部から送らせたフォームはトークンが無いか間違っていて、必ず拒否されます。

## 対策2: SameSite=Lax Cookie

Cookieに `SameSite=Lax` を付けると、ブラウザは「他のサイトから始まったPOSTリクエスト」にそのCookieを付けなくなります。Cookieが付かなければ、サーバーから見るとログインしていないリクエストになるので、操作は実行されません。

`Lax` は、リンクをクリックして移動するようなふつうのGETにはCookieを付けるので、使い勝手を大きく損ないません。そのかわり、GETで状態を変えてしまうと守れないので、「更新・削除・ログアウトなど状態を変える操作は必ずPOSTにする」ことが前提になります（このアプリのログアウトもPOSTです）。

## なぜ両方使うのか

SameSiteはブラウザ側の仕組みなので、古いブラウザや、同じサイトの別のサブドメインからのリクエストなど、守れない場面があります。CSRFトークンはサーバー側で確実に確認できるので、両方を組み合わせて「多層防御」にします。

## やってみよう（自分のアプリの中で確かめる）

1. ログインしてメールアドレスを変更すると、正常に更新されます。
2. ブラウザの開発者ツールで、フォームの隠し項目 `csrf_token` の値を書き換えてから送信すると、「403 Forbidden」になります。トークンの照合が効いていることがわかります。
3. 開発者ツールの「Application（アプリケーション）→ Cookies」で、`session` Cookie に `SameSite: Lax` と `HttpOnly` が付いていることを確認しましょう。

## 実際の開発では

Flaskでは、自分でトークンを実装するかわりに `Flask-WTF` の `CSRFProtect` を使うのが一般的です。
