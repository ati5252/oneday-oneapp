# Day 4: パスワードの安全な保存とログイン

## 動かし方（Windows / PowerShell）

いつものようにリポジトリを最新にしてから起動します。

```powershell
# リポジトリを最新にする
Set-Location C:\Users\maxim\oneday-oneapp
git pull

# Day 4 のフォルダに移動して、Flask を入れて起動する
Set-Location day04-password-storage
py -m pip install flask
py app.py
```

ブラウザで http://127.0.0.1:5000 を開き、「ユーザー登録はこちら」から好きなユーザー名とパスワード（8文字以上）を登録してください。ログインすると、データベースに実際に保存されている値が表示されます。データは `app.py` の隣にできる `users.db` に入ります（Git には含めません）。止めるときは PowerShell で `Ctrl + C` です。

使っているのは Flask と Python の標準ライブラリ（`hashlib`、`hmac`、`secrets`、`sqlite3`）だけです。

## パスワードをそのまま保存すると何が困るのか

ログインのしくみを作るとき、いちばん素直なのは「登録されたパスワードをデータベースにそのまま入れておき、ログインのときに入力と見比べる」方法です。動きはしますが、データベースの中身が外に漏れた瞬間、全員のパスワードがそのまま読まれてしまいます。

データベースの漏えいは、Day 1 の SQL インジェクションのような攻撃だけでなく、バックアップファイルの置き忘れや、権限を持つ人の持ち出しでも起こります。そして多くの人は同じパスワードを他のサービスでも使い回しているので、被害はこのアプリだけで終わりません。つまり「漏れないようにする」だけでなく「漏れても読めないようにしておく」ことが必要です。

## 速いハッシュでもまだ足りない理由

そこで、パスワードを「ハッシュ関数」で別の文字列に変換して保存します。ハッシュは元に戻せない一方向の変換で、ログインのときは入力も同じように変換して、結果が一致するかを比べます。

ただし、MD5 や SHA-256 のような一般的なハッシュ関数は「速く計算できる」ように作られています。ファイルの改ざんチェックなどにはその速さが長所ですが、パスワードでは短所になります。攻撃者は漏れたハッシュを元に戻すことはできなくても、「よくあるパスワードを片っ端からハッシュにして、一致するものを探す」ことはできます。速いハッシュなら、ふつうのパソコンのGPUでも1秒間に何十億回も試せるので、短いパスワードや辞書にある単語はすぐに見つかってしまいます。

もう一つの問題は、同じパスワードが同じハッシュになることです。「password123」を使っている人が100人いれば、データベースには同じハッシュが100個並びます。攻撃者は1回計算するだけで100人分を一度に見つけられますし、よくあるパスワードとハッシュの対応表（レインボーテーブル）を前もって作っておくこともできます。

## 対策1: ソルト付きの遅いハッシュ（scrypt）

`app.py` の `hash_password()` は、2つの工夫でこれらの問題に対応しています。

一つ目は「ソルト」です。ユーザーが登録するたびに `secrets.token_bytes(16)` でランダムな値を作り、パスワードに混ぜてからハッシュにします。ソルトが人ごとに違うので、同じパスワードでもハッシュはまったく違う値になります。前もって作った対応表は使えなくなり、攻撃者は1人ずつ別々に計算しなければなりません。ソルトは秘密ではないので、ハッシュと一緒に保存して構いません。

二つ目は、わざと「遅い」ハッシュ関数を使うことです。`hashlib.scrypt` は、1回の計算にたくさんのメモリと時間を使うように作られた、パスワード専用の関数です。このアプリの設定（`n=2**15`）では1回に約32MBのメモリを使い、0.1秒ほどかかります。正しいパスワードを知っている本人が1回ログインするだけなら気にならない時間ですが、何十億回も試したい攻撃者にとっては、とても大きな壁になります。メモリをたくさん使うので、GPU などで大量に並べて計算する方法も効きにくくなっています。

保存される文字列は `scrypt$32768$8$1$ソルト$ハッシュ` という形です。計算の設定も一緒に入れておくことで、あとから設定を強くしても、古い設定で保存したユーザーのハッシュをきちんと確かめられます。さらに、ログインに成功したときに `needs_rehash()` で設定が古いと分かれば、手元にある正しいパスワードで新しい設定のハッシュに作り直しています。

## 対策2: 時間差の出ない比較

ハッシュ同士を `==` で比べると、Python は先頭から1文字ずつ比べ、違う文字が見つかった時点でやめます。そのため「何文字目まで合っていたか」によって、かかる時間がほんの少しだけ変わります。この差を大量に測ると、正しい値を少しずつ推測できてしまうことがあります（タイミング攻撃）。

`verify_password()` では、`hmac.compare_digest()` を使って比べています。これは、どこで違っていても最後まで同じように比べるので、時間から中身を推測されません。Day 2 で CSRF トークンを比べたときと同じ考え方です。

## 対策3: ユーザーがいるかどうかを教えない

ログインに失敗したとき、「そのユーザーはいません」と「パスワードが違います」を分けて表示すると、攻撃者は登録されているユーザー名を調べられてしまいます。このアプリでは、どちらの場合も「ユーザー名またはパスワードが違います」という同じメッセージにしています。

メッセージをそろえても、かかる時間が違えばばれてしまいます。ユーザーがいないときにハッシュの計算を省くと、その分だけ返事が速くなるからです。そこで、ユーザーがいないときも、起動時に作っておいた `DUMMY_HASH` を相手に同じ scrypt の計算をして、時間をそろえています。

## 対策4: ログインの回数制限

どれだけハッシュを遅くしても、ログイン画面に向けて何度でもパスワードを試せるなら、よくあるパスワードはいつか当たってしまいます。このアプリでは、同じユーザー名、または同じ接続元（IPアドレス）で、5分間に5回失敗すると、それ以上はパスワードを調べずに「429 Too Many Requests」で断ります。5分たてば古い失敗は数えなくなり、またログインできるようになります。

ユーザー名ごとに数えるのは、1人のアカウントを集中的に狙われるのを防ぐためです。IPアドレスごとに数えるのは、1か所からたくさんのユーザー名を順番に試されるのを防ぐためです。

ただし、回数制限には注意点もあります。ユーザー名だけで止めると、攻撃者がわざと失敗を繰り返して、本人をログインできなくする嫌がらせができてしまいます。実際のサービスでは、止める時間を少しずつ長くする、CAPTCHA を出す、本人にメールで知らせるなど、いくつかの方法を組み合わせます。

## そのほかの細かい工夫

- 登録時にパスワードの長さを8文字以上にしています。ハッシュをどれだけ強くしても、短すぎるパスワードは試す数が少なくて済むからです。
- ユーザー名とハッシュをデータベースに入れるときは、Day 1 と同じく `?` のプレースホルダを使っています。
- 登録・ログイン・ログアウトのフォームは、Day 2 と同じ CSRF トークンで守っています。
- ログインに成功したら `session.clear()` でセッションを作り直しています。

## やってみよう（自分のアプリの中で確かめる）

1. ユーザーを登録してログインすると、ホーム画面に保存されている値が表示されます。どこにもパスワードそのものが無いことを確認しましょう。
2. 一度ログアウトし、別のユーザー名で「同じパスワード」を登録してみます。ログインして表示される値を比べると、ソルトもハッシュもまったく違うことが分かります。
3. 登録していないユーザー名でログインしたときと、登録したユーザー名で間違ったパスワードを入れたときで、表示されるメッセージが同じことを確認しましょう。
4. わざと5回続けてパスワードを間違えると、6回目は正しいパスワードを入れても断られます。開発者ツールの「Network（ネットワーク）」タブで、ステータスが 429 になっていることも見てみましょう。5分待つか、アプリを再起動すると元に戻ります。

## 実際の開発では

自分でハッシュの形式を作るかわりに、ライブラリに任せるのが一般的です。Flask と一緒に入っている Werkzeug には `werkzeug.security.generate_password_hash()` と `check_password_hash()` があり、ソルトの生成と scrypt での計算、時間差の出ない比較までまとめてやってくれます。ほかに、Argon2 を使う `argon2-cffi` や `bcrypt` もよく使われます。

設定の強さは、OWASP（Webセキュリティの団体）の「Password Storage Cheat Sheet」が目安になります。scrypt なら `n=2**17` 以上が推奨されていて、このアプリの `2**15` は、手元で軽く動かすために少し弱めにしています。

回数制限も、`Flask-Limiter` のような拡張を使うと、アプリを再起動しても記録が消えない保存先（Redis など）を選べます。
