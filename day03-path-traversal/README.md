# Day 3: パストラバーサル（ディレクトリトラバーサル）対策

## 動かし方（Windows / PowerShell）

Day 1 で clone したリポジトリを最新にしてから起動します。

```powershell
# リポジトリを最新にする
Set-Location C:\Users\maxim\oneday-oneapp
git pull

# Day 3 のフォルダに移動して、Flask を入れて起動する
Set-Location day03-path-traversal
py -m pip install flask
py app.py
```

ブラウザで http://127.0.0.1:5000 を開くと、メモの一覧が出ます。初回起動時に、`app.py` の隣に `files` フォルダとサンプルのメモが自動で作られます。止めるときは PowerShell で `Ctrl + C` です。

## パストラバーサルとは

「ファイル名をURLやフォームで受け取って、そのファイルを表示・ダウンロードする」機能はよくあります。サーバーの中では、決まったフォルダ（このアプリなら `files`）とユーザーが送ったファイル名をつなげて、ファイルを開きます。

問題は、ファイル名がユーザーの自由に送れる値だという点です。パスの世界では「`..`」が「ひとつ上のフォルダ」を意味します。もしファイル名に `..` とフォルダの区切り記号が混ざっていると、つなげたパスは `files` フォルダから外へ出て、上の階層へ「さかのぼって（traverse）」しまいます。その結果、設定ファイルやパスワードの入ったファイル、プログラムのソースコードなど、見せるつもりのなかったファイルを読まれてしまいます。

さらに、名前の途中ではなく最初から「絶対パス」（`C:\` や `/` で始まるパス）を送られた場合、Python の `os.path.join` は前半のフォルダを捨てて、絶対パスの方を採用します。つまり「フォルダ名を前につけているから安全」とは言えません。

Windows では区切り記号が `/` と `\` の2種類あり、ドライブ名（`C:`）や `CON` のような特別なデバイス名もあるので、気をつける点がさらに増えます。また、URLエンコード（`%2e` など）で文字を隠して送られることもあるため、「`..` という文字列が含まれていたら拒否」のような単純な文字列チェックでは、抜け道が残りがちです。

## 対策1: ファイル名の許可リスト

`app.py` の `SAFE_NAME` は、「英数字・`_`・`-` だけで64文字まで、拡張子は `.txt` か `.md`」という形を正規表現で決めています。`resolve_safe_path()` は、送られた名前の「全体」がこの形に一致しないと 400 で拒否します。

ポイントは、「ダメな文字を探して消す（拒否リスト）」のではなく、「OKな形だけを通す（許可リスト）」にしていることです。許可リストなら、`/`、`\`、`:`、`..`、ヌル文字など、攻撃に使える記号は最初から形に含まれていないので、URLエンコードやWindows特有の書き方を一つずつ思いつかなくても、まとめて入れなくなります。

あわせて、`CON.txt` や `NUL.md` のような Windows のデバイス名も拒否しています。Windows ではこれらがファイルではなく装置として扱われることがあるためです。

## 対策2: 本当の場所を確かめる

許可リストだけに頼らず、最後に「実際に開く場所」も確かめます。`os.path.realpath()` は、`..` やシンボリックリンク（別の場所を指すショートカットのようなもの）をすべて解決して、ファイルの本当の場所を求めます。そのうえで `os.path.commonpath()` を使って、その場所が `files` フォルダの中にあるかを確認し、外なら 400 で拒否します。

これで、たとえば `files` フォルダの中に外を指すリンクが置かれてしまった場合でも、リンク先の本当の場所が外なので拒否できます。

比べるときに文字列の `startswith` を使わないのも大事です。`files` で始まるかどうかだけを見ると、`files_backup` のような「名前がたまたま同じ文字で始まる別のフォルダ」を見逃してしまいます。`commonpath` はフォルダの単位で比べるので、この間違いが起きません。

対策1と対策2は役割が違います。対策1は「おかしな名前を入口で止める」、対策2は「万一すり抜けても、外のファイルは開かない」という最後の砦です。どちらか一方の書き方を将来変えてしまっても、もう一方が守ってくれる「多層防御」になっています。

## 対策3: ふつうのファイルだけを開く

`os.path.isfile()` で、開こうとしているものが「ふつうのファイル」であることを確認し、フォルダや存在しないものは 404 にしています。エラーの画面には、サーバーの中のパスやエラーの詳しい中身を出さないようにしています。パスの情報も、攻撃者にとってはヒントになるからです。

## やってみよう（自分のアプリの中で確かめる）

1. 一覧からメモをクリックすると、中身が表示されます。アドレスバーの `?name=` の後ろがファイル名になっていることを確認しましょう。
2. `name=` の値を、一覧に無い名前（たとえば `memo.txt`）に変えると、「404 Not Found」になります。
3. `name=` の値に、フォルダ名を区切り記号（`/` や `\`）でつなげた名前や、`app.py` のような許可されていない拡張子を入れてみると、ファイルを探しに行く前に「400 Bad Request」で止まります。
4. `files` フォルダに自分で `.txt` ファイルを追加し、ブラウザを更新すると、一覧に出てきて表示できます。日本語の名前やスペース入りの名前は許可リストの形に合わないので、一覧に出ません。どこまで許すかを決めるのが許可リストの考え方です。

## 実際の開発では

Flask では、ファイルを返すときに `send_from_directory(フォルダ, ファイル名)` を使うのが一般的です。これは内部で `werkzeug.security.safe_join` を使い、フォルダの外へ出るパスを拒否してくれます。アップロードされたファイルを保存するときは、`werkzeug.utils.secure_filename()` で名前を整えてから使います。

さらに良いのは、ユーザーにファイル名そのものを送らせない設計です。たとえばデータベースに「ID 1 番 = welcome.txt」のように登録しておき、URLではIDだけを受け取れば、パスを組み立てる場面そのものが無くなります。
