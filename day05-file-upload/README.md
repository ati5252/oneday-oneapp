# Day 5: 安全なファイルアップロード

## 動かし方（Windows / PowerShell）

いつものようにリポジトリを最新にしてから起動します。

```powershell
# リポジトリを最新にする
Set-Location C:\Users\maxim\oneday-oneapp
git pull

# Day 5 のフォルダに移動して、Flask を入れて起動する
Set-Location day05-file-upload
py -m pip install flask
py app.py
```

ブラウザで http://127.0.0.1:5000 を開くと、ファイルを選んでアップロードできる画面が出ます。使えるのは PNG・JPEG・GIF の画像、PDF、テキスト（.txt）で、1MB までです。アップロードしたファイルは `app.py` の隣にできる `storage` フォルダに、ファイルの情報は `uploads.db` に入ります（どちらも Git には含めません）。止めるときは PowerShell で `Ctrl + C` です。

使っているのは Flask と Python の標準ライブラリ（`os`、`re`、`secrets`、`sqlite3`）だけです。

## ファイルアップロードの何が危ないのか

これまでの Day では、ユーザーが送ってくるのは名前やパスワードのような短い文字列でした。ファイルアップロードでは、ユーザーは「ファイル名」と「中身」の両方を自由に決めて送ってきます。しかもサーバーはそれをディスクに書き込み、あとで他の人にも配ります。気を付けることが多いのはそのためです。

よくある失敗は、大きく分けて4つあります。

一つ目は、サーバーの上でプログラムとして動かされてしまうことです。PHP のように「公開フォルダに置いた `.php` ファイルがそのまま実行される」しくみのサーバーで、アップロードされたファイルを公開フォルダに保存すると、攻撃者は自分で書いたプログラムをサーバーに送り込んで動かせてしまいます。Flask では `static` フォルダの中身は誰でも URL で読めるので、そこに保存するのも危険です。

二つ目は、他のユーザーのブラウザで悪いスクリプトが動いてしまうことです。HTML や SVG（画像の一種ですが、中に JavaScript を書けます）をアップロードされ、それをこのサイトのページとして開かれると、Day 2 で見たような「他人になりすました操作」が、もっと直接にできてしまいます。拡張子が `.png` でも中身が HTML の場合、ブラウザが中身を見て「これは HTML だ」と推測して表示してしまうことがあります（コンテントスニッフィング）。

三つ目は、ファイル名を使った攻撃です。ファイル名に `../../app.py` のような値を入れられると、Day 3 のパストラバーサルと同じように、保存先の外のファイルを上書きされるおそれがあります。同じ名前で何度も送られて、他の人のファイルを上書きされることもあります。

四つ目は、サーバーの資源を使い果たされることです。とても大きなファイルや、たくさんのファイルを送られると、メモリやディスクがいっぱいになり、アプリが止まってしまいます。

## 対策1: 大きさの制限

`app.config` の `MAX_CONTENT_LENGTH` を 1MB にしています。これを設定すると、Flask はリクエストの中身を読み込む前に大きさを確かめ、上限を超えていれば「413 Payload Too Large」で断ります。大きなファイルを全部メモリに読み込んでから「大きすぎた」と気付くのでは遅いので、入り口で止めることが大切です。

あわせて、保存できるファイルの数も `MAX_FILES`（50個）までにしています。1つ1つが小さくても、無限に送られればディスクは埋まってしまうからです。

## 対策2: 拡張子の許可リスト

受け付ける拡張子を `ALLOWED_TYPES` に書いた種類だけにしています。Day 3 と同じく「危ないものを禁止する」のではなく「安全だと分かっているものだけを許可する」考え方です。`.php` や `.exe` を禁止するリストを作っても、`.phtml` や `.PhP` のような書き方の違いや、思いつかなかった種類がすり抜けてしまいます。

拡張子は、ファイル名の最後の「.」より後ろだけを、小文字にして調べています。`photo.png.php` は最後が `php` なので断られますし、`PHOTO.PNG` は `png` として受け付けます。SVG と HTML は、中に JavaScript を書けるので、許可リストにわざと入れていません。

## 対策3: 中身のシグネチャを確かめる

拡張子はただのファイル名の一部なので、中身が HTML のファイルを `cat.png` という名前にするのは簡単です。また、ブラウザがアップロードのときに一緒に送る「このファイルは image/png です」という情報（`uploaded.content_type`）も、ユーザーが自由に書き換えられます。どちらも信用できません。

そこで `content_matches()` で、ファイルの先頭のバイトを確かめています。多くのファイル形式は、先頭に決まったバイト列（シグネチャやマジックナンバーと呼ばれます）を持っています。PNG なら `\x89PNG\r\n\x1a\n`、JPEG なら `\xff\xd8\xff`、GIF なら `GIF89a`、PDF なら `%PDF-` で始まります。拡張子が `.png` なのに先頭がこの形でなければ、「中身が拡張子と合いません」として断ります。テキストファイルには決まった先頭が無いので、「UTF-8 として読めること」と「NUL 文字（`\x00`）を含まないこと」で確かめています。

ただし、先頭の数バイトが正しくても、その後ろに別のデータを付け足すことはできます。シグネチャの確認は「明らかに違うものをはじく」ためのもので、これだけで完全に安全になるわけではありません。だからこそ、次の対策4と5を組み合わせます。

## 対策4: 保存名はサーバーが決め、公開フォルダの外に置く

ユーザーが送ってきたファイル名は、保存には一切使っていません。保存するときの名前は `secrets.token_hex(16)` で作ったランダムな32文字に、確かめた拡張子を付けたもの（例: `storage/5b3ba6b2...e0cd12.png`）です。これで、ファイル名に `../` や `C:\` が入っていても関係なくなり、Day 3 のパストラバーサルは起こりません。他の人と同じ名前のファイルを送っても上書きされませんし、ファイルを開くときの `"xb"` モードは、万が一同じ名前があればエラーにして上書きを防ぎます。ランダムな名前なので、他の人のファイルの URL を推測されることもありません。

元のファイル名は、一覧に表示するためだけにデータベースへ入れています。そのときもフォルダの部分を取り除き、改行などの制御文字を消して、長さを100文字までにしています。画面に出すときは Jinja2 の自動エスケープが効くので、`<script>.txt` のような名前でも HTML としては解釈されません。

保存先の `storage` フォルダは、Flask が自動で公開する `static` フォルダとは別の場所です。ファイルを見るには必ず `/files/<ID>` の処理を通るので、ID の形のチェック、データベースでの確認、そして次の対策5のヘッダーが毎回かかります。

## 対策5: 安全なヘッダーを付けて返す

`/files/<ID>` でファイルを返すときは、ブラウザが「このファイルをどう扱うか」を決めるヘッダーを、すべてサーバー側で決めています。

`Content-Type` には、アップロードのときにブラウザが送ってきた値ではなく、シグネチャを確かめたうえで決めた種類（`image/png` など）を付けます。さらに `X-Content-Type-Options: nosniff` を付けて、ブラウザが中身を見て勝手に種類を推測しないようにしています。テキストファイルの中身が `<script>...` であっても、`text/plain` として、ただの文字として表示されます。

`Content-Disposition` は、ブラウザの中で開く（`inline`）か、ダウンロードさせる（`attachment`）かを決めるヘッダーです。このアプリでは、画像だけを `inline` で表示でき、PDF とテキストは必ず `attachment` でダウンロードさせます。ダウンロードされたファイルは、このサイトのページとしては開かれないので、中に何が入っていてもこのサイトの Cookie などには触れられません。日本語のファイル名も、Flask が `filename*=UTF-8''...` という形に正しくエンコードしてくれます。

最後に `Content-Security-Policy: default-src 'none'; sandbox` を付けています。これは「もしこのファイルがページとして開かれても、スクリプトは一切動かさず、別のサイトから来たものとして扱う」という指示です。ここまでの対策をすり抜けられたときのための、最後の守りです。

## そのほかの細かい工夫

- アップロードのフォームは、Day 2 と同じ CSRF トークンで守っています。
- データベースに値を入れるときは、Day 1 と同じく `?` のプレースホルダを使っています。
- `/files/<ID>` の ID は、Day 3 と同じく正規表現で「32文字の16進数」だけを受け付け、開くパスはデータベースに入っている ID と拡張子だけから組み立てています。

## やってみよう（自分のアプリの中で確かめる）

1. 好きな PNG や JPEG の画像をアップロードして、「表示」で開いてみましょう。一覧の「保存名」が、元の名前とはまったく違うランダムな名前になっていることを確認します。
2. メモ帳で `<h1>hello</h1>` とだけ書いたファイルを作り、`test.png` という名前で保存してアップロードしてみます。「ファイルの中身が拡張子と合いません」と断られるはずです。
3. 同じ内容のファイルを `test.txt` という名前でアップロードし、「ダウンロード」してみます。開発者ツールの「Network（ネットワーク）」タブでレスポンスヘッダーを見ると、`Content-Type: text/plain`、`Content-Disposition: attachment`、`X-Content-Type-Options: nosniff` が付いていることが分かります。
4. 1MB より大きなファイルを選んでアップロードすると、「413」で断られることを確かめましょう。
5. `.svg` や `.html` のファイルを選んでみると、拡張子の許可リストで断られます。

## 実際の開発では

- 画像なら、Pillow などのライブラリで一度開いて、本当に画像として読めるかを確かめ、さらに作り直して保存（再エンコード）すると、後ろに付け足されたデータや、写真に入っている位置情報（Exif）も取り除けます。小さなファイルなのに開くと巨大な画像になる「解凍爆弾」にも気を付けます。
- ファイルの種類の判定には `python-magic` などのライブラリもよく使われます。
- 大きなサービスでは、アップロードされたファイルを Amazon S3 のようなストレージに置き、アプリとは別のドメイン（例: `usercontent.example.com`）から配ります。万が一スクリプトが動いても、本体のサイトの Cookie には届かないからです。
- 不特定の人からファイルを受け取るなら、ウイルス対策ソフトでの検査も組み合わせます。
- OWASP の「File Upload Cheat Sheet」に、ここで紹介した対策がまとまっています。
